# Platform game port: decisions, fixes and fidelity notes

Scope: the hoverboard platform game in `web/js/platformer/`, ported from the 2009 Flash source
(`reference/Junior_Game/src/ebug/*.as`, `src/ebug/junior/*.as`) following
`reference/analysis/flash-platformer.md` (cited below as "spec section N"). Merged into
`web/NOTES.md` (sections 3, 10.1 and 12, cited there as [PD]), which is the entry point and wins
where the two differ. Levels 2 to 10 are in `web/NOTES-levels-decisions.md`. Everything not listed
here is meant to behave as the original did.

## Module layout

| File | Role |
|---|---|
| `constants.js` | Type ids, states, event ids, timings, scoring (Constants.as, Event.as, GameEntity.as). |
| `vec.js` | Vector3 rounding semantics (add rounds to 0.001; subtract/multiply do not). |
| `physics.js` | ParticleSystem: Verlet boxes, gravity, drag, force friction, maxChange clamp, collision order, world bounds. |
| `timeline.js` + `data/clips.js` | Flash timelines (labels, frame scripts, bounds) at 25 fps; `clips.js` is generated by `tools/extract-timelines.mjs`. |
| `entities.js` | GameEntity AI (walk, idle, fall, safeToMove, onSolidGround) and the microbes (good, Lucy, bad, superinfection). |
| `player.js` | PlayerEntity: accelerate/brake, jumps, soap/white blood cells, camera, antibiotic, damage. |
| `actors.js` | Bullets, camera flash, pickups, milk glass, portal, antibiotic bomb. |

Data: `tools/convert-levels.mjs` writes `web/data/levels/<name>.json`, `tile_definitions.json`
and `index.json` (play order from `GameController.as:65-69` and the `next=` chains).

## Timing

- **Steady 30 ms logic steps.** The original ran one UPDATE per two 15 ms `main()` calls
  (`PlatformGame.as:613-616,1163`; spec section 1.4) but slowed down when Flash could not keep up.
  The port runs one logic step every two 15 ms engine ticks and interpolates drawing in between.
- **Level timer in steps.** The original counted `getTimer()` wall-clock seconds
  (`PlatformGame.as:558-569`). The port uses 6000 steps (180 s), so replays are deterministic.
- **Animation clock.** Flash timelines advance at 25 fps on a global 40 ms frame clock driven by
  the 30 ms steps (3 frames every 4 steps), so every `midAnimation` gate keeps its original length
  in milliseconds (jump start 160 ms, hurt 480 ms, soap shot 120 ms).
- **Antibiotic fuse** 2000 ms of `getTimer()` (`AntibioticBombEntity.as:33,46`) becomes 67 steps.
- **Frame-script semantics** (spec section 11 says they are only certain to within a tick): a
  `gotoAndPlay` queues the destination frame's script and a second goto before it runs replaces it.
  This reproduces the spec's observation that Slurm is removed immediately after `be_killed`
  (section 4.5). Unit tests pin the durations.

## Feel improvements (deliberate changes)

- **Jumping.** Edge-triggered jumps with a 4-step (120 ms) buffer and 4-step coyote time.
  Pressing jump after landing always works: the original's "dead press" after a double jump
  (`PlayerEntity.as:180-184,418-419,432`; spec 3.4) and lost quick taps are gone. The double jump
  is kept (two jumps, re-armed on landing, also available after walking off a ledge, and a
  bad-microbe contact still restores them). A jump within the coyote window of standing on
  something always restores the full double jump. Holding jump still does not re-jump on landing.
  `options.jumpFeel = false` restores the original behaviour (unit tests cover both).
- **Camera.** Same margins (screen x 250 and 450, `PlatformGame.as:45-46`), but the view eases
  towards the target (25% per step) instead of moving by exactly the player's last step, is
  clamped to `[0, cols*50 - 800]`, and no longer pans the wrong way when leaving a margin (spec
  section 7). It is part of the simulation because on-screen status drives solidity and AI. Shake
  is a render-only offset (`camera.shakeX/Y`).
- **Auto-repeat.** Fire and camera repeat while held after about 510 ms, every 60 ms, like the
  keyboard auto-repeat that re-triggered Flash's key-down flags. The player's animations still
  limit the real rate (one soap per 120 ms animation, one photo per flash).
- **Controls mapping.** Fire throws soap (white blood cells in body levels); camera takes a photo
  or, while an antibiotic is carried, throws it. The original used Up = jump, Space = throw and
  Ctrl = photo. The brief puts jump on Space (Up and W still jump), so throw moved to X / J, and
  Ctrl is back on the camera as in the original (C / K / Ctrl / Shift; `DEFAULT_KEYS` in
  `settings.js`). Prompts advertise the first binding (C), because Ctrl + arrow is an OS shortcut
  on some systems. A key map is saved only once the player remaps keys, so default changes reach
  everyone else.
- **Prompts follow the device.** Intro text that named keys ("press the CTRL button", "Press
  SPACE BAR") now uses placeholders filled from the live bindings (`web/js/ui/prompts.js`): "press
  C" on a keyboard, "tap the camera button" on touch, "press B" on a gamepad.
- **Camera look-ahead.** While riding, the margin window slides up to 70 px against the direction
  of travel (eased), so more of what lies ahead is visible. It lives in the simulation camera
  (tile solidity and entity freezing follow the view), depends only on simulation state, and is
  the same for every player (`options.cameraLookAhead`, 0 turns it off).
- **Juice** (cosmetic, `fxRng` only, never read by the simulation): squash and stretch about the
  hoverboard on jump, double jump, land and hurt; hoverboard exhaust bubbles; dust on landing;
  hit-stop (whole logic steps held back in the scene: 4 on hurt, 3 on a kill, 2 on a photo, so a
  run is identical for the same per-step inputs, and the 180 s level clock, counted in steps, pauses
  with it: at most a few tenths of a second per level); light shake on hurt, kills, the portal and
  explosions (scaled by reduced shake); white hit flashes; red-tinted blinking while
  invulnerable; splat and bubble particles; star sparkles on pickups and photos; a sparkle that
  flies from each photographed microbe to its ePhone tick box, which fills when it lands; score
  popups; eased HUD counters; a tick badge over microbes already photographed; haptics on hurt,
  kills, goal ticks and the portal. Reduced motion (setting or `prefers-reduced-motion`) turns
  off squash and stretch, the photo screen flash, the portal's breathing and rings, the sparkle
  flights, the typewriter, the phone's grow and shrink (a fade instead) and the iris (a fade), and
  thins particles; reduced shake scales shake to a quarter.
- **Portal.** The shipped art is one pulsing blue ellipse that looked the same open or closed
  (spec 4.10; only the ePhone picture changed). Added: a closed portal is drawn dimmed and greyed;
  opening it plays a chime, a burst of stars, shockwave rings and a banner ("The portal is
  open!"), the ePhone picture flips to the exit picture and the phone wiggles; an arrow at the
  screen edge points to an open portal that is off screen.
- **Level end.** Entering the open portal draws the player into it (spin and shrink), an iris
  closes on the portal, then a summary card shows score (counting up), photos, time and lives
  with Next level, Play again and Quit. The simulation state is `complete` from the step the
  portal fires; the scene's `ui` becomes `complete` when the card appears.
- **Sound.** The original was silent (no sound tag in any of the 71 SWFs, flash-swf-assets.md
  section 6), so every effect is synthesised (`audio.js` SYNTHS) and each area has a procedural
  loop (`web/js/core/music.js`, a cheerful F major tune for the kitchen), started once audio is
  unlocked by a gesture and ducked under menus.

## Kept faithful (documented quirks)

- Physics: Verlet with `add()` rounding to 0.001 and the 0.1 px x snap after every step, so
  coasting settles at +1.0 / -0.9 px per step and never stops (spec 2.2); one constraint iteration
  with the stale centre for dynamic pairs; smaller-penetration push direction (head bumps are
  ceilings, ledge corners push sideways); no one-way platforms; the world floor at `450 - h`;
  only tiles overlapping the visible 800 px band are solid; off-screen entities freeze; forces
  keep accumulating on physics-exempt bodies.
- Derived numbers match the spec exactly: jump -25, -46.05, -63.35 ... apex -99.79 at step 8;
  run 3.6, 7.1, 10.4 ... capped at maxChange (21.16 in Lucy levels, 23.98 with Iggy, else 25);
  bullets 19.5, 28.5, then 10 + maxChange per step (484 px or 538 px over 16 steps).
- Rules: infinite ammo from the start (pickups give +7 and ammo only); levels 1-4 throw white
  blood cells (missing `body_level` means a body level); the +3 "bullet hits bad microbe" points
  are never awarded; the first overlapping microbe takes the photo even if already photographed;
  PHOTOGRAPH_GOOD also counts good deaths; KILL_ALL ignores `microbeType`; antibiotic kills do
  not count for KILL_ALL; every bad-microbe touch costs a life and kills the microbe only if it
  is idle or walking; 480 ms of no control and no damage after a hit; microbes see only anchor
  cells; the Lucy/milk result depends on entity order; score persists across levels. (Decision
  11.9 #10 later turned the +3 bonus on: `web/NOTES-levels-decisions.md` section 1.)
- **Amy and Harry are not identical.** Their SWFs have different upper-body frame scripts
  (`movies/amy.swf` sprite 208 vs `movies/harry.swf` sprite 193): Amy's throw fires on frame 4
  (160 ms, Harry frame 3) and keeps the upper body busy for 18 frames (720 ms, Harry 120 ms), so
  she throws at most about once every 0.7 s; her photo pose clears `midAnimation` after 7 frames
  (Harry 15), although the flash's 10-step fade still sets the photo cooldown. Hurt (480 ms) and
  jump timings are the same. Kept as in the original.
- **The avatar's live width.** Flash read `playerEntity.clip._width` at the moment a shot or
  photo was handled, and that is the union of the upper and lower body at their current frames:
  the hoverboard exhaust behind the board (move, accelerate) and the brake sparks in front of it
  widen it a lot. So a photo taken while riding right lands about 20 to 40 px further ahead than
  one taken standing (standing: player x + 55.7; riding in `accelerate_mid`: + 78.7 to + 92.4).
  `tools/extract-timelines.mjs` exports every frame's bounds of `<who>_upper` / `<who>_lower`
  from the SWFs (`frameBounds` in `data/clips.js`) and `AvatarClip.bounds` unions them, so the
  flash and soap spawn points, the player's hitTest box (portal, pickups) and the off-screen test
  all follow the art as in the original (`PlatformGame.as:681,721,763,802`). Checked against the
  Ruffle captures `reference/captures/ruffle-level1-photo-standing.png` (offset about 55) and
  `ruffle-level1-photo-riding-right.png` (offset at least 75); unit tests pin both.
- **The upper body is already animating when play starts.** `ClipLoader.as:17` plays the upper
  body's `hurt` flourish on load (hidden behind the ePhone intro); its last frame goes to `move`,
  so the level starts with the upper body looping `move`. The port starts it on `move` directly
  (the intro does not advance the simulation's clips). The lower body stays stopped on frame 1,
  as in the original. Logic states are unchanged (`upperState` stays IDLE).
- **Depth order.** Level entities (portal, pickups, microbes, milk) are attached inside the
  `game` clip when the level is built, and each tile cell is duplicated above them when it first
  scrolls into view (`PlatformGame.as:419,1104`), so tiles cover the level entities: the exit
  portal's bottom 14 px sit behind the worktop (`ruffle-level1-portal-closed-tile-over-portal.png`).
  Projectiles and the flash are attached later, above the tiles already on screen, so the port
  draws them after the tiles. The avatar is a root clip (depth 6) above the whole `game` clip
  (depth 4), so it is drawn last, over projectiles too (a soap bubble leaves from behind the
  hand). The review suggested drawing the player before the projectiles; the SWF's depths say
  the player is on top, so the port follows the SWF.
- **Goal type 0 vs 3** (spec 5.4): `alpha_level1.xml` says `goalType="0"` (photograph Lucy); the
  documentation's 3 is wrong. The data keeps 0.

## Differences in flow (for the flow controller)

- **Game over.** The task asked for "restart the same level"; the scene's "Try again" does that
  and keeps the score. The original restarted the *round* from its first level
  (`GameController.as:283-308`, `PlatformGame.as:187-192`; spec 9.2). The scene accepts
  `params.onGameOver(result)` and `params.onComplete(result)` so the flow controller can restore
  round restarts and hand over to the game show and kitchen game.
- **Briefing** (`intro.js`). Recreated with the original art: the HUD ePhone grows and turns to
  landscape (e_phone frames 10-29 through `tracks.group`), shows the level_intros pages on its big
  screen (`tracks.bigScreen`; level 1 stops at frames 1, 3, 6, 9, 14, 20 and 30, so the host,
  camera, Lucy and portal pictures match their pages) and shrinks back (frames 40-59). The text
  is drawn in the original text boxes (matrices read from sprite 1479) from
  `web/data/lang/en/levels.json`, with a typewriter reveal. Tap anywhere, Space / jump or Enter first
  shows the whole page, then turns it; Esc skips; the 5 s autoplay is kept but counts from when
  the text is fully shown (young readers need the time). Since the whole-game review (NOTES 10.6)
  it waits the greater of 5 s and 0.45 s a word, times the text scale, stops once the child turns
  a page, and never turns the last page, so the level starts only with the child's press. The phone key or button, or tapping the
  HUD phone, re-opens it and pauses. The original's stacked autoplay intervals (bug 23) do not
  exist here. Levels whose pages are not in the atlas yet show the text on the blank big screen.
  The page text is drawn in the original's regular-weight white Arial (titles bold Arial 16;
  `level_intros` DefineEditText 1200-1232), falling back to the platform's sans-serif where
  Arial is missing, as Flash did for device fonts. There is no dimmed backdrop; while the first
  briefing is up only the background, the level's entities and the HUD show around the phone (the
  original had not built any tiles yet: `INIT_DIALOGUE` never reaches `RENDER_WORLD`,
  `PlatformGame.as:540-551,1090-1107`); the re-opened briefing (port only) shows the whole level.
  Play and the level clock start as the phone starts shrinking, as the original did
  (`PlatformGame.as:545-549`), so the level runs under the phone as it turns away; a re-opened
  briefing resumes once the phone has gone. The autoplay stops while the window is blurred or
  hidden and restarts with the player's next key or tap. Port additions around the phone use the
  game's UI font: the Skip / Back and Next buttons, page dots, the autoplay bar and the control
  hint under the phone (on a dark pill so it reads on any background). The small and large
  ePhone art has the "e-Bug" wordmark removed (third-party branding, `GOAL_PROMPT.md:166`).
  Spelling slips in the original wording are corrected ("with out", "Bodys", "isnt'",
  "Pennicilium", "defenses" to British "defences"); the wording is otherwise unchanged.
- **HUD** (`hud.js`) is drawn on the canvas from the original art at the original root-timeline
  positions (spec 8.1, 8.3): score clip with four digit clips, three hearts, the timer, the ePhone
  with the status screen (goal picture, camera icon, six tick boxes), and the exit picture once
  the portal opens. The timer is the original field's style: bold black Arial 16, left-aligned at
  x 333.95 with Flash's 2 px gutter (DefineEditText 1499). Hearts go from the left, as the
  original hid `heart0` first (`PlatformGame.as:598-601`); a lost heart bursts, then is hidden.
  Differences: the timer shows the real time from the start (the original showed "90" until the
  first second passed); it gains the platformer SWF's unused `timer` stopwatch clip to its left,
  and in the last 20 s the number turns red and pops each second (juice; the original stayed
  black); a lost heart's burst is added (the original hid it at once); the ePhone's "e-Bug"
  wordmark is removed (third-party branding, `GOAL_PROMPT.md:166`); the score counts up and clamps at 0 to 9999 (the original's four digit clips
  showed -10 as "0990", bug 19; the probe keeps the true score); in touch play the ePhone moves to
  the left edge, because the thumbs and action buttons cover the bottom right, and the touch
  pause and phone buttons sit in the empty top-left corner. Keyboard play keeps the original
  layout exactly. A hidden live region mirrors lives, score, time and goal for screen readers.
- **Background.** Filled with the original flat #ff9900 (root shape 1495) for every level; the
  shape's 1 px outline is dropped (it showed as a dark frame on letterboxed screens).

## Unverified

- Flash Player's real `setInterval(15)` cadence inside a 25 fps movie (spec 11); the port assumes
  30 ms steps.
- Frame-script ordering within a tick (spec 11). Durations are pinned by unit tests.
- Entity clip sizes other than the avatar's are frame-1 bounds. Flash's `_width`/`_height`
  change per frame (a microbe's walk, the flash's fade), and the original read them live in
  `safeToMove`, the ground test and hitTest; the port reads frame 1 for microbes, pickups and
  projectiles. Physics boxes use the creation-time values, as the original did. (The avatar's
  live width is now reproduced and verified against Ruffle; see "Kept faithful".)

## Engine and platform (review of the level 1 slice)

- **Input device.** The game starts in touch mode on any device with a touchscreen
  (`(pointer: coarse), (any-pointer: coarse)`), so touchscreen laptops get the controls too. Any
  touch or pen press anywhere switches to touch (a capture-phase `pointerdown` listener), so the
  on-screen controls come back after a key press on a phone with a keyboard; a mouse press
  switches to keyboard. Previously only a press on a (hidden) control could bring them back.
- **Pausing when away.** Besides a hidden tab, losing window focus (`blur`) and turning a phone to
  portrait (the "turn your device sideways" prompt, same media query) open the pause menu, and
  in portrait the loop stops ticking (the level clock, microbes and the briefing's autoplay all
  wait) until the phone is turned back. The pause menu stays up, so the player chooses when to
  resume.
- **Paused means frozen.** While paused or while the briefing is re-opened, the picture under
  the card stays still: particles, popups, shake, sparkles in flight, HUD counters and the
  animation clock wait. Only the HUD's touch / keyboard layout keeps following the device.
  Restart, Play again and Try again clear popups and shake as well as particles.
- **Settings are overrides.** Only what the player sets is saved (`smw:settings`, schema 2), so
  changes to the defaults (key bindings) reach every player who never changed them. Reduced
  motion and reduced shake follow `prefers-reduced-motion` live until the player sets them with
  the new Reduce motion / Reduce shake toggles in the pause menu. Settings saved by earlier
  builds (the whole merged object) are migrated: values equal to today's defaults, the
  OS-derived motion flags and the full key map are dropped.
- **Tap targets.** DOM buttons live in the 800 x 450 UI layer, which is scaled down on landscape
  phones (0.83 at 667 x 375). Their minimum size is now `max(48px, 46px / --stage-scale)` in
  stage units, so every button is at least 44 CSS px on screen (an E2E test checks the briefing,
  pause and game-over buttons at 667 x 375) and tablets keep the larger size.
- **Controls over targets.** The camera is part of the deterministic simulation, so it does not
  make room for the thumb controls (desktop and phone runs must stay identical). Instead a
  control fades to 25% opacity while a live microbe, pickup, the milk or the portal is under it,
  and is still fully usable. The letterbox bars on common phones (75 to 91 px) are narrower than
  the control clusters (172 to 240 px), so moving the clusters into them would not clear the
  playfield; they stay where they are. The touch bot run checks every step that a control over
  a target is faded.
- **Keyboard in dialogs.** Pause, level-complete and game-over cards are `aria-modal`; Tab and
  Shift+Tab cycle through their buttons without leaving the card; Space and Enter activate the
  focused button natively (the engine no longer cancels Space and Tab inside a card); arrow keys
  move as before; closing a card returns focus to the game canvas. The game-over prompt names the
  device's key ("Press Enter to try again", "Tap to try again", "Press A to try again").
- **Rendering cost.** The canvas backing store is capped at 2 device pixels per CSS pixel (the
  atlases are drawn at 2x) instead of 2.5, and a governor lowers it in steps (to 0.85, 0.7 and
  0.55 of that, never below 1 per CSS pixel) while the rolling render time is above 12 ms, and
  raises it again below 5 ms. It is off while tests step the loop by hand. The closed portal's
  tint is still applied per frame: caching tinted copies of its animated frames would cost
  several MB of texture memory for a draw that only happens while the portal is on screen.
- **Offline cache and updates.** The service worker is registered when play first starts, so its
  downloads do not compete with the level's. It precaches the shell, every level JSON and the
  level 1 atlases with the default avatar (2.5 MB); other atlases (the other avatar, later
  areas) are cached the first time the game fetches them. The 512 px icons and the notes files
  are not cached. Updates wait: without `skipWaiting()`, an open tab keeps the worker and cache
  of the build it started with, and a new build takes over once every tab of the game has been
  closed, so old modules never meet new data. `clients.claim()` only affects the first visit.
- **Deterministic tests.** `?manual=1` keeps the loop from ticking in real time, so the E2E
  tests step every tick from the first one (they assert `stepCount` is 0 when they start).
